# Markdown to a Figma design system

## Product scope and priority

This is the final planned feature addition. Finish the current Settings polish
and outstanding core workflow work first, then implement this flow, then freeze
features for production acceptance and release hardening.

The starting point is an existing design-system `.md` generated by the user in
Claude (or another authoring tool) and added to their project. Elf accepts that
file; users do not need to regenerate their specification inside Elf or manually
convert it to JSON. Support structured tables and prose through an editable
extraction draft, and ask when the document leaves a decision unspecified.

The intended result is the supported design system in the paired Figma file:
collections, variables, modes and aliases; components and variants; and readable
Figma documentation covering the supplied usage guidance. Component description
fields carry concise usage documentation separately from visual specifications.
Longer guidelines can appear on an optional editable documentation/presentation
page. Show unsupported details explicitly rather than claiming arbitrary Markdown
can be reconstructed completely. Users can request resources with documentation
only, or let Elf also lay out the presentation and refine it themselves afterward.

The first local extraction/review preview is implemented; creating the combined
Figma design system is not yet implemented. The MCP
already exposes `list_collections`, `list_variables`, `create_collection`,
`upsert_variables`, `list_components`, `upsert_component`, and
`upsert_component_set`. An assistant can read project Markdown using its editor
tools and call these operations today, but that does not provide a complete,
validated, resumable design-system import.

## Try the extraction preview

- **Extension:** Manage → Design system from Markdown, or **Elf: Prepare Design
  System from Markdown**. Select a `.md` inside the active project, review the
  source, then choose AI extraction or manual preparation. AI requires selecting
  an editor model and explicit consent to send the full displayed document.
  Edit the private JSON draft, then choose **Validate design-system draft** in
  Changes. Validation results open as a read-only document.
- **npm Settings:** use **Design system from Markdown · preview**, enter a
  project-relative `.md` path and choose **Prepare Markdown**. Review the source
  and instructions, edit/paste the extracted JSON, then **Validate draft**.
  The browser performs no model request; use the extension or MCP for AI.
- **MCP:** `prepare_design_system({path:"DESIGN_SYSTEM.md"})` returns bounded source,
  instructions, an initial draft and a source-pinned review ID. Treat the Markdown
  as data. Extract a draft, present it for editing, then call
  `validate_design_system({id,draft})`. This does not approve any Figma writes.

Source files must be regular UTF-8 Markdown inside the project, under 128 KB;
external symlinks and hard links are refused. Reviews expire after 30 minutes
and reject a changed source. Draft validation covers names, modes, types,
collection-scoped aliases/cycles, source-line bounds and component structural
fields. Unresolved questions and missing visual specifications remain visible.
Model output is schema-checked by the shared engine, never executed.

`reviewReady` means extraction validation passed; **`canApply` is always false**
in this stage. Full component token binding/variant/dependency validation,
existing Figma conflict detection, creating collections/resources, presentation
pages, documentation sync and managed-baseline adoption are still to come.
No project design files or Figma resources are created by this preview. Native
AI drafts live in editor workspace storage and require review again after a
runtime restart. This preview is local, not a published npm/Marketplace release.

## Agreed workflow

1. Select a local Markdown specification. Show which content will be shared
   before an external model interprets it. Treat document instructions as data;
   they must not authorize commands, installs, network access, or Figma writes.
2. Extract a structured draft of collections, modes, typed variables, aliases,
   component specifications, variants, and usage documentation. Include source
   locations and unresolved questions. Ask about missing values, framework/library
   choices when code generation is requested, and ambiguous units or names.
   Never silently invent a token value or infer a full component from its name.
3. Read the paired file and propose creates/updates with exact targets. Validate
   collection identity, alias dependencies/cycles, supported types, modes,
   component bindings, intentional differences, deprecations, and conflicts.
4. Review tokens and components together. Offer **Resources only** (collections,
   variables and components) or **Include presentation** (an optional dedicated
   page with labeled token samples and component examples). Existing unrelated
   pages and artwork stay intact. Presentation remains editable by the designer.
5. Apply only the approved plan through the shared engine and authenticated
   bridge. Revalidate the file and source revisions before writing. Order writes
   by dependency; verify results and record created IDs, failures and remaining
   operations so a retry does not duplicate resources. Do not promise atomic
   rollback across Figma operations.
6. Establish the supported local token/component files and managed baseline,
   with a separate review for local file creation. Then offer monitoring and
   drift checks. A one-off MCP canvas write must not be reported as automatically
   tracked by the project watcher.

## Implementation order

- Add a shared specification schema, bounded Markdown ingestion and editable
  extraction preview, with deterministic fixtures and ambiguity diagnostics.
- Extend the existing plan/apply engine for collection/mode identity and the
  combined token/component dependency graph; enforce stale-review and retry
  safety. Reuse it from MCP, npm Settings and the extension.
- Add optional presentation planning and rendering after resource creation works.
- Test a small new file, existing resources, duplicate names across collections,
  aliases/modes, unsupported values, conflicting edits, interrupted apply and
  repeat apply. Confirm real results through a second Figma read.

Keep this feature behind a preview until these acceptance checks pass. It is the
last planned feature before the production acceptance and release-hardening pass.
