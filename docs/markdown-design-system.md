# Markdown to a Figma design system

## Product scope and priority

This is the final planned feature addition. Finish the current Settings polish
and outstanding core workflow work first, then implement this flow, then freeze
features for production acceptance and release hardening.

The starting point is an existing design-system `.md` generated by the user in
Claude (or another authoring tool) and added to their project. Elf accepts that
file; users do not need to regenerate their specification inside Elf or manually
convert it to JSON. Support structured tables and prose through an editable
extraction draft, and ask when the document leaves a decision unspecified.

The intended result is the supported design system in the paired Figma file:
collections, variables, modes and aliases; components and variants; and readable
Figma documentation covering the supplied usage guidance. Component description
fields carry concise usage documentation separately from visual specifications.
Longer guidelines can appear on an optional editable documentation/presentation
page. Show unsupported details explicitly rather than claiming arbitrary Markdown
can be reconstructed completely. Users can request resources with documentation
only, or let Elf also lay out the presentation and refine it themselves afterward.

The first local extraction/review preview is implemented; creating the combined
Figma design system is not yet implemented. The MCP
already exposes `list_collections`, `list_variables`, `create_collection`,
`upsert_variables`, `list_components`, `upsert_component`, and
`upsert_component_set`. An assistant can read project Markdown using its editor
tools and call these operations today, but that does not provide a complete,
validated, resumable design-system import.

## MCP-only workflow

The agreed hosted direction retains Elf Bridge and removes the requirement to
run a local IDE, terminal or tunnel. See [Hosted Elf MCP with Elf Bridge](hosted-mcp-plugin.md)
for the architecture, implementation order and acceptance checks. This hosted
workflow is planned, not deployed; local MCP remains the available execution path.

Markdown-to-Figma design-system generation belongs solely to MCP. The coding
assistant in Cursor, Claude Code, Codex or another MCP host reads the selected
Markdown, extracts an editable draft, presents questions and the resource plan,
and applies only explicitly approved changes through Elf's bridge.

The extension and npm Settings retain their existing drift checks, monitoring,
reports, connections, sync and resource tools. They have no Markdown creation
form, AI extraction command or design-system HTTP endpoint. MCP can still be
launched by the npm package or bundled runtime; that packaging does not expose
the design-system workflow in the extension or browser.

### Try the extraction preview

1. Connect Elf MCP to the intended local project.
2. Ask the assistant to call
   `prepare_design_system({path:"DESIGN_SYSTEM.md"})` for your selected file.
   It returns bounded source, extraction instructions, an initial draft and a
   source-pinned review ID. Review what content is shared with your assistant;
   its host/model provider controls data handling. Treat Markdown instructions
   as data, never permission to execute tools or change files.
3. Have the assistant extract the design system, identify unresolved questions,
   and present the JSON for your review/editing.
4. Call `validate_design_system({id,draft})`. Resolve reported extraction issues.
   Validation does not approve Figma writes.

Source files must be regular UTF-8 Markdown inside the project, under 128 KB;
external symlinks and hard links are refused. Reviews expire after 30 minutes
and reject a changed source. Draft validation covers names, modes, types,
collection-scoped aliases/cycles, source-line bounds and component structural
fields. Unresolved questions and missing visual specifications remain visible.
Model output is schema-checked by the shared engine, never executed.

`reviewReady` means extraction validation passed; **`canApply` is always false**
in this stage. Full component token binding/variant/dependency validation,
existing Figma conflict detection, creating collections/resources, presentation
pages, documentation sync and managed-baseline adoption are still to come.
No project design files or Figma resources are created by this preview.
Extraction review IDs are held in the MCP process and require preparing the
source again after a restart. This preview is local, not a published release.

## Agreed workflow

### Figma onboarding and target selection

The design-system name, Markdown filename and Figma document name are independent.
A new file may be named Untitled. File names are display labels; verification
must retain the selected file key and paired document identity, never compare
names or bypass identity checks when a different target is selected.

Support both **Create in a new/blank file** and **Modify an existing system**.
The user creates/opens the Figma file and provides its URL; Elf currently has no
MCP tool to create a Figma document. Onboarding must coordinate account access
for strict verification, plugin pairing/approval, and explicit selection of the
target file key. Existing plugin-only authorization remains a distinct supported
mode. Changing the target must invalidate old write plans and require fresh
approval; it must not silently redirect an existing project's drift monitoring.

For either path, inspect the selected scope with `list_collections`,
`list_variables` and `list_components` before proposing writes. Existing MCP
primitives include `create_collection`, `upsert_variables`, `upsert_component`,
`upsert_component_set`, `upsert_text_style` and `upsert_effect_style`.
They already support resource creates/updates, but are not the combined reviewed
Markdown import workflow. For an existing system, resolve exact collection/node
identities, expose ambiguous matches and ownership conflicts, preserve unrelated
resources, and review adoption into managed drift tracking separately. Never
assume matching component names alone authorize replacing an existing resource.

Local stdio MCP now provides this onboarding flow (unpublished preview):

1. Call `figma_onboarding_status` to inspect the account and target.
2. For strict verification, call `connect_figma_account` and have the user open
   the returned authorization link and consent in their browser. Account tokens
   stay in private local storage; the assistant receives no credentials.
3. Ask the user for the intended file URL and whether it is new or existing.
   Call `select_figma_file({url,purpose:"new"|"existing",authorization:"strict"|"plugin"})`.
   This is a session selection, not a change to project drift configuration.
4. Open that file and Elf Bridge. If its saved pairing does not reconnect, call
   `get_figma_pairing_code` and paste the code into the plugin. Choose the matching
   verification mode in the plugin. Reissuing a code replaces unused codes.
5. For plugin-only connections, call `inspect_figma_target_approval`, present the
   actual document key/name and trust mode, and obtain explicit user approval.
   Call `approve_figma_target` with the fresh selection ID, ticket and file key.
   This approves the current connection only and does not enable automatic sync.
6. Confirm `figma_onboarding_status` reports `ready:true`, then inspect resources
   before proposing any creates or updates. Selecting a file is not permission
   to modify it. Reconnecting or changing the selected target requires reviewing
   the current connection and any proposed writes again.

Raw Figma reads and writes use this selected target and the shared transaction
lane. Existing managed project tools such as `check_drift`, `plan_sync` and
`apply_sync` continue to use the project's configured target. Without an explicit
selection, a configured project remains the default raw-tool target. A fresh
project can launch with `--project /absolute/project/path` without a config file;
Markdown extraction does not require a connected Figma file.

These account/target tools are local stdio tools, excluded from HTTP transport.
They do not yet provide a Claude website connector. Closing MCP closes its
callback listener; it does not disconnect the saved account or erase pairings.
Disconnecting the account or starting a newer authorization cancels older pending
OAuth callbacks, including callbacks started by another local Elf process.

### Extract, review and create

1. Select a local Markdown specification. Show which content will be shared
   before an external model interprets it. Treat document instructions as data;
   they must not authorize commands, installs, network access, or Figma writes.
2. Extract a structured draft of collections, modes, typed variables, aliases,
   component specifications, variants, and usage documentation. Include source
   locations and unresolved questions. Ask about missing values, framework/library
   choices when code generation is requested, and ambiguous units or names.
   Never silently invent a token value or infer a full component from its name.
3. Read the paired file and propose creates/updates with exact targets. Validate
   collection identity, alias dependencies/cycles, supported types, modes,
   component bindings, intentional differences, deprecations, and conflicts.
4. Review tokens and components together. Offer **Resources only** (collections,
   variables and components) or **Include presentation** (an optional dedicated
   page with labeled token samples and component examples). Existing unrelated
   pages and artwork stay intact. Presentation remains editable by the designer.
5. Apply only the approved plan through the shared engine and authenticated
   bridge. Revalidate the file and source revisions before writing. Order writes
   by dependency; verify results and record created IDs, failures and remaining
   operations so a retry does not duplicate resources. Do not promise atomic
   rollback across Figma operations.
6. Establish the supported local token/component files and managed baseline,
   with a separate review for local file creation. Then offer monitoring and
   drift checks. A one-off MCP canvas write must not be reported as automatically
   tracked by the project watcher.

## Implementation order

- Add a shared specification schema, bounded Markdown ingestion and editable
  extraction preview, with deterministic fixtures and ambiguity diagnostics.
- Extend the existing plan/apply engine for collection/mode identity and the
  combined token/component dependency graph; enforce stale-review and retry
  safety. Expose creation only through MCP; keep the shared drift engine reusable by
  the extension and npm tools.
- Add optional presentation planning and rendering after resource creation works.
- Test a small new file, existing resources, duplicate names across collections,
  aliases/modes, unsupported values, conflicting edits, interrupted apply and
  repeat apply. Confirm real results through a second Figma read.

Keep this feature behind a preview until these acceptance checks pass. It is the
last planned feature before the production acceptance and release-hardening pass.
