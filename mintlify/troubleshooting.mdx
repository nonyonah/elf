title: "Troubleshooting"
description: "Resolve common setup and sync problems."
---

## Pairing code invalid or expired

Use the latest code from the runtime connected to this project. Codes are single-use. Reopen the current public plugin build if it retains an old UI. Never paste pairing codes into public support threads.

## Hosted MCP approval page is blank

Close the old authorization tab and reconnect from your assistant using `https://elf.riftlabs.xyz/mcp`. The rendering fix is deployed; reload without the browser cache if necessary. See the [hosted connector walkthrough](/hosted-mcp) for plugin approval and finishing the connection. Share only redacted error text, never the authorization URL or pairing code.

## Hosted MCP logo is missing

Elf includes its mascot in MCP icon metadata, but the assistant controls whether it displays it. Claude has an [open issue about custom connector icon support](https://github.com/anthropics/claude-ai-mcp/issues/152); removing and re-adding the connector is not a reliable fix. The logo is also the favicon on [Elf Settings](https://elf.riftlabs.xyz/settings).

## File does not match

Check the configured Figma file URL and the document currently open in the plugin. File identity is the key, not the display name. Select the intended target explicitly.

## File not verified

For strict mode, reconnect Figma and confirm that the authorized account can access the file. Alternatively, explicitly select plugin-only approval when appropriate. Do not silently downgrade verification.

## Port already serves a different bridge

Stop only the bridge you own, or choose a free port. Do not share or expose bridge secrets to get around authentication. The standard public plugin expects port 8765; a custom port also requires a compatible plugin endpoint.

## Sync needs review

Inspect conflicts, unknown token references, deprecated entries, and missing component descriptions. Regenerate stale reviews. Automatic sync does not bypass these safeguards.

## Figma rate limits

Keep the plugin connected for supported document operations. Respect REST retry instructions when account verification is limited. Repeated reconnects are not a rate-limit bypass.

## Support

File an issue at [GitHub](https://github.com/nonyonah/elf/issues) with your package version, operating system, and redacted error. Do not include credentials or private design-system documents.

## Add file reports an expired or unavailable review

Use the link from the intended assistant in the browser where you connected it. Elf now retains separate assistant permissions in the same browser and includes the assistant identity in file and plan review links. A link alone never grants access.

If the connection predates this fix and another assistant replaced its browser session, reconnect the affected assistant once and request a fresh Add file link. Existing links cannot restore lost browser authority. Expired grants and missing plugin connections now show specific recovery messages.

## Extension starts in one workspace but not another

Install the maintainer-provided Elf 0.3.26 VSIX (or update through the Marketplace once that version is published), then run **Developer: Reload Window** in VS Code. The fix selects the machine-wide bridge identity before loading project dotenv files; an old `mcp/.env` token no longer silently gives a project a different identity. Explicit shell overrides remain supported.

A legacy bridge may need one restart: stop Elf watchers and local MCP clients, stop the old bridge from the original installation/project, then start the updated extension. Never copy bridge secrets between projects or force-stop a host used by other clients. Existing saved credentials are not deleted; the plugin may need pairing with the new identity. Startup failures now report safe recovery instructions instead of only “Elf is not ready.”
